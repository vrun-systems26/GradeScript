How to use this page

The problem, in one picture

Today: one detection idea gets hand-written 3 times (Splunk, Sigma, Elastic) and the copies can drift apart. With ShieldQL: you write it once, and the 3 versions are generated from that one source, so they can't disagree with each other.

Navigating it (30 seconds)

  1. Pick a rule from the "Load example" dropdown, top right.
  2. Panel 1 (left) is the rule itself, in plain syntax. Edit it — everything else updates instantly.
  3. Panel 2 (right) shows that same rule translated into 3 real tools. Click the pill buttons to switch between them.
  4. Panel 3 (bottom) runs the rule against 7 pretend security events live, so you can see exactly which ones it catches.

Quick glossary

Splunk
A tool companies use to search huge piles of computer activity logs and set up alarms on them.
Sigma
Not a tool — a shared, open way of writing down an alarm idea so people using different tools can trade rules with each other.
Elastic / EQL
Another company's log-search tool, similar job to Splunk, own language called EQL.
SOC
"Security Operations Center" — the team that watches for attacks all day.
DSL
"Domain-Specific Language" — a small language built for one job only (here: writing security rules), instead of a general-purpose language like Python.
Rule
One "if this happens, flag it" statement — the thing you write in panel 1.
Compile / transpile
Automatically translating one piece of code into another language without a human rewriting it by hand.
within (honest note)
Sets a time window on the rule (e.g. within 10m) and gets passed to each target's own time-window syntax. The live tester below evaluates one event at a time — it doesn't yet simulate a real multi-event time window itself.
